# 测开面试题库（围绕本项目）

用法：每题先看「考察点」自己答一遍，再对照「回答骨架」。**能说清楚取舍和局限，比背功能列表值钱得多。**
方括号里的路径是对应代码位置，面试官追问时可以直接翻。

## 一、开场定位

### 1. 用 30 秒介绍这个项目
**考察点**：能不能分清「写用例」和「造框架」。
> 「这是一个我自己写的轻量级接口自动化测试框架。核心解决的是**用例之间的数据依赖和执行编排**问题：用例用 YAML 声明 `depends_on`，框架做拓扑排序和环检测，同层并发、跨层串行，上游提取的变量自动注入下游请求。另外做了加载期静态校验、21 种断言算子（含 Schema 契约校验）、软断言和单文件 HTML 报告。项目里还有 67 个单测和 4 个 Python 版本的 CI 来保证框架本身的质量。」

### 2. 为什么不用 pytest / HttpRunner，要自己写？
**考察点**：是否理解工具边界，而不是「重复造轮子」。
> pytest 的收集模型是扁平的测试项，用例间的依赖编排和「同层并发」不是它的原生抽象；HttpRunner 功能完整，但我想可控地实现 DAG、软断言、重试粒度和结果结构，也借这个过程把执行引擎的设计吃透。**框架自身的测试仍然用 pytest**，两者不冲突。代价是放弃了 pytest 的插件生态，这点我承认。[`docs/architecture.md` ADR-1]

### 3. 和 HttpRunner / Postman / pytest 的本质区别？
> Postman 是手工/集合级工具，不适合进 CI 做工程化；pytest 是通用测试运行器；HttpRunner 是成熟的完整框架。FlowTest 是**学习性的最小实现**，差异集中在三点：显式 DAG 依赖编排（含环检测和 Skip 传播）、加载期变量数据流静态校验、以及「报告/断言/执行」三层解耦可替换。我没有做参数化、Web 平台、多协议这些，规模差很多。

### 4. 这个项目最难的部分？
> 不是发请求，是**让错误可诊断**：① 变量依赖要能在加载期就查出「引用了没人产出的变量」；② 上游失败要能精确传播跳过原因，而不是下游报一堆看不懂的 401；③ 断言失败和传输失败要分开处理，否则重试会把真 bug 洗掉。

### 5. 如果重做会改什么？
> 加用例级 `setup/teardown` 和数据池，让用例尽量自包含，把 DAG 从「必需品」降级成「业务流程编排的可选项」；再加参数化矩阵和 JUnit XML 输出接现有 CI 平台。[`docs/architecture.md` 已知局限]

## 二、框架设计

### 6. DAG 怎么实现？复杂度？为什么分层？
> 入度=依赖数，每轮取所有入度 0 的节点组成一层，层内无依赖可并行、层间串行保证变量确定；O(V+E)。分层而不是扁平顺序，是为了给并发提供安全的边界。[`core/resolver.py`]

### 7. 环检测怎么给出具体环路径？
> Kahn 发现「本轮没有入度 0 节点」只能说明有环；我额外做一次**三色标记 DFS**，遇到灰色节点就从栈里截出环路径，报 `a -> b -> c -> a`，排查快很多。

### 8. 上游失败，下游怎么处理？
> 执行每个 case 前检查依赖状态，非 PASSED 直接标记 SKIPPED 并记录具体是哪个依赖失败，结果里带 `skip_reason`。`fail-fast` 模式下，后续层即使不依赖失败用例也整体跳过。[`core/runner.py::_run_case`]

### 9. 变量怎么跨用例传递？为什么要命名空间？
> 上游 `extract` 写入 `Context["<case_id>.<var>"]`，下游用 `${login.token}` 引用。命名空间让来源可静态推导，所以加载期能校验引用是否有人产出，也避免同名变量被覆盖。[`core/context.py`]

### 10. 为什么整串 `${count}` 要保留原始类型？
> 如果统一转成字符串，`expect: ${expected_total}` 会变成 `"3"`，和响应里的整数 `3` 比较就假失败了。所以 `render()` 判断整个字符串是否恰好是单个 token，是就直接返回原对象（int/bool/list）；只有嵌在字符串里才做文本替换。[`core/context.py::render`]

### 11. 软断言解决什么问题？什么时候不该用？
> 一个大响应里多个字段同时错，硬断言遇错即停，要跑 N 遍才看全；软断言一次收集全部失败点，报告里逐条列出。但如果后续断言依赖前一步的结果（比如先取 id 再查详情），软断言会产生连带噪声，这种场景要用硬断言或拆用例。[`core/assertor.py::run`]

### 12. Schema 契约校验和逐字段断言的区别？
> 逐字段断言验证「这个场景下对不对」；Schema 验证「结构本身合不合规」（必填字段、类型、取值范围、枚举）。接口悄悄加/删/改字段时，Schema 会直接报出出错的 JSON 路径，比断言 `None` 清楚得多。两者互补，不是替代。

### 13. 加载期静态校验都查什么？为什么重要？
> id 唯一、依赖存在且无环、算子名合法、JSONPath 语法、Schema 文件存在且合法、变量引用是否有人产出。**错误前置**：第 17 个用例写错不该等前 16 个 HTTP 请求跑完才发现，尤其在 CI 里一轮要几分钟。[`core/loader.py::check_suite`]

### 14. 并发执行用例有什么坑？
> ① `requests.Session` 非线程安全 → `threading.local()` 每线程独立；② 共享变量/token 竞争 → 变量按命名空间写入，且只在层结束后才被下游读取，跨层严格串行；③ 用例间数据污染（同一订单被并发改）→ 靠 `depends_on` 显式声明顺序；④ 日志交错 → 统一 logger + 用例 id 前缀。

### 15. 重试策略？为什么断言失败不重试？
> 仅连接异常/超时/5xx 指数退避重试，且每次重新渲染 `${{uuid()}}` 生成新数据。**断言失败是产品信号**，重试可能让它偶然通过，制造 flaky 测试并掩盖 bug。报告里保留完整重试轨迹。[`core/runner.py::_execute`]

## 三、Python 与工程能力

### 16. 为什么用 `threading.local()`？
> 层内用线程池并发，Session 若共享会有连接池状态和 Cookie 串扰；thread-local 让每线程懒加载自己的 Session，同时线程内复用 keep-alive 连接。[`core/client.py`]

### 17. 断言算子注册表怎么实现？好处？
> 类变量 `OPS: dict[str, Callable]` + `@Assertor.register("eq")` 装饰器，函数定义即注册。新增算子只加一个函数，loader 通过 `available_ops()` 自动拿到合法算子名做静态校验，消除一长串 if/else。[`core/assertor.py`]

### 18. `MISSING` 哨兵是什么，为什么不用 `None`？
> 响应里 JSON `null` 和「这个路径根本不存在」是两件事：`is_null` 对前者应为真，`exists` 对后者应为假。用单例哨兵区分，避免把「字段被删了」误判成「字段值为空」。[`core/context.py`, `core/extractor.py`]

### 19. 为什么全用 dataclass？
> 模型层无 IO、无第三方依赖，字段和默认值一目了然，`asdict` 式序列化方便报告层；类型注解在 3.10+ 下配合 `from __future__ import annotations` 不产生运行时开销，也让静态检查能发现问题。

### 20. `lru_cache` 用在哪？
> JSONPath 表达式编译结果。`$.data.items[*].id` 这类表达式在多个用例/多次重试里重复出现，编译一次缓存复用。[`core/extractor.py::_compile`]

### 21. 为什么要分 5 种自定义异常？
> runner 需要据此决定**错误是否可重试**：`CaseLoadError`/`DependencyError` 是用例定义问题（直接终止），`VariableNotFoundError` 是编排问题，`RequestError` 是传输问题（可重试），`ExtractError` 是表达式问题。用一堆 `except Exception` 会把不可恢复的错误也重试掉。[`core/errors.py`]

### 22. 有 GIL，线程池并发还有意义吗？
> 有。接口自动化测试是 **IO 密集型**，请求等待期间线程释放 GIL，线程池能有效缩短整体耗时；CPU 密集型才需要多进程。本项目 17 个用例本地 <1s，主要收益在真实网络延迟下才明显。

## 四、测试理论与用例设计

### 23. ⭐ 用例之间有依赖，是不是反模式？
**这题几乎必问，答不好会显得只会堆功能。**
> 「是，需要谨慎。链式依赖的问题有三个：一个失败带崩一串、用例不能单独重跑、执行顺序变成隐式契约。所以我在项目里把 DAG 定位为**业务流程型用例的编排能力**（登录→下单→查询→取消这类天然有状态流转的场景），而单元型接口用例建议保持独立、自包含测试数据。更彻底的解法是 `setup/teardown` + 数据池 + 唯一数据生成（`${{uuid()}}`），让每个用例自己造数据，把依赖降级成可选项；这也是我 Roadmap 的第一条。」

### 24. 给你一个「创建订单」接口，怎么设计用例？
> 按维度展开，别只想到「成功」：
> - **功能**：正常创建、必填校验、金额计算（含浮点/折扣边界）、库存扣减、重复提交
> - **参数**：等价类 + 边界值（quantity = 0 / 1 / stock / stock+1 / 负数 / 超长字符串 / 类型错误）
> - **异常**：未登录、token 过期、书不存在、库存不足、服务 5xx、超时
> - **幂等**：同一 request_id 重复提交是否只产生一单
> - **并发**：同一库存并发下单是否超卖
> - **安全**：越权查他人订单、SQL 注入 / XSS 入参、敏感信息是否脱敏
> - **契约**：响应结构用 JSON Schema 校验
> 项目里的 `04_negative_retry.yaml` 和 `03_order_flow.yaml` 就是这套思路的落地。

### 25. 幂等性怎么测？
> 同一业务键连续请求 N 次，断言：副作用只发生一次（订单数、库存扣减）、返回一致或明确返回「已处理」；并发场景下用线程池同时发，检查是否出现重复记录。注意先确认接口的幂等键是 request_id 还是业务主键。

### 26. flaky 测试怎么治理？
> 先分类：环境抖动（网络/依赖服务）→ 加有上限的重试 + 重试轨迹；用例自身有状态依赖 → 拆掉依赖、自造数据；异步时序 → 用显式等待替代固定 sleep；共享数据竞争 → 隔离数据。重试只是兜底，**不能用来掩盖不稳定**，所以我给重试加了「断言失败不重试」的硬约束，并在报告里保留每次尝试。

### 27. 覆盖率怎么看？100% 覆盖意味着没 bug 吗？
> 不意味着。覆盖率只说明代码被执行过，不说明断言是否有效、边界是否覆盖、业务规则是否正确。我更关注**接口契约覆盖、异常路径覆盖、关键业务场景覆盖**；项目里用覆盖率是防止框架自身的分支（环检测、skip 传播、重试）没人测到，不是拿数字当 KPI。

### 28. 怎么区分「环境问题」和「真 bug」？
> 分层看：连接拒绝/超时/5xx → 环境（可重试）；4xx 且符合预期 → 正常负向用例；4xx/200 但断言失败 → 产品或契约问题。报告里保留原始响应、耗时、重试轨迹和跳过原因，就是为了快速做这个归因。

## 五、工程化与质量

### 29. 测试框架自己怎么测？
> 三层：① 纯函数单测（DAG、渲染、算子、取值）；② 用 FakeClient 测调度逻辑（skip 传播、重试、fail-fast、变量流），不发真实请求，快且确定；③ 起内置 Demo 服务跑完整 17 个用例的集成测试，并断言报告内容（通过率、脱敏、重试轨迹）。共 67 个用例。[`tests/`]

### 30. CI 怎么设计？
> push/PR 触发 → 4 个 Python 版本矩阵 → `ruff` 静态检查 → `pytest --cov` → `flowtest validate`（纯静态，不发请求）→ `flowtest demo`（端到端）→ 上传 HTML 报告 artifact（失败时也传，`if: always()`）。报告作为 artifact 的意义是：失败时不用重跑就能看到现场。[`.github/workflows/ci.yml`]

### 31. 为什么不用 Allure？
> 需要 Java/服务/额外命令，clone 的人常常跑不起来，CI artifact 不能双击就看。单文件报告零依赖、可直接分享。代价是没有历史趋势和多批次对比，这一条我会主动说明。[`docs/architecture.md` ADR-6]

### 32. 用例失败了，你的报告怎么帮人定位？
> 失败用例默认展开；逐条列出断言的 op / 取值路径 / 期望 / 实际 / 说明；保留完整请求（头脱敏）与响应体；有重试就展示每次的 HTTP 状态和耗时；跳过的用例写明是哪个上游失败。基本不用重新跑一遍。

## 六、压力追问

### 33. ⭐ 这个项目是不是参考/借鉴了别人的？
**照实说，别含糊，也别背台词。**
> 「设计思路上参考了 HttpRunner 的 YAML 数据驱动和 extract/validate DSL、pytest 的 fixture 可组合理念、REST Assured 的断言表达，这些我在 README 的『设计参考与致谢』里写明了，**代码是从零写的，没有复制任何项目源码**。我做它的目的是把执行引擎的设计搞明白，所以特意选了和成熟框架不同的切入点——显式 DAG 编排和加载期变量数据流校验。要说我跟 HttpRunner 的差距，主要在参数化、多协议和平台化，这些我没做。」

> ⚠️ 千万别说「完全独立设计、没参考任何东西」——面试官一问 DSL 为什么长这样就会露馅；也别把开源项目 fork 来改 README 当成自己的，commit 历史和细节追问都过不了。**大方标注参考 + 讲清自己的取舍，反而是加分项。**

### 34. 用例涨到 1000 个，你的框架会怎样？
> 瓶颈在：① 单进程线程池 → 要分布式执行/分片（按 tag 或 DAG 切分）；② 全量报告单文件 → 要分片 + 汇总 + 持久化历史；③ 变量池全在内存 → 要外部存储或按分片隔离；④ 加载期校验仍要 O(V+E)，1000 个没问题，但报告渲染会变重，需要流式/分页。另外要加用例级别的超时、速率限制和失败重跑单用例的能力。

### 35. 这项目有什么不足？
> 主动说 3 条就够：没有用例自包含数据（对 DAG 依赖偏重）、没有执行历史与趋势、只支持 HTTP/JSON 且并发模型简单。然后接「所以 Roadmap 第一条就是 setup/teardown + 数据池」。[`docs/architecture.md` 第 4 节]

### 36. 被测服务直接挂了会怎样？
> 所有用例报 `RequestError` → ERROR（不是 FAILED，语义区分开），依赖它们的下游全部 SKIPPED 并写明原因，报告照常生成，进程退出码非 0 让 CI 变红。不会假装通过，也不会因为重试把故障洗掉。
